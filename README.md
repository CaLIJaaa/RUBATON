# RUBA - закрытый обмен на трёх ZK-рынках

Кто какие роли играет, какие есть сценарии и что уже готово, описано в [бизнес-логике](docs/BUSINESS_LOGIC.md). Как вручную пройти все экраны и роли: [MANUAL_TEST_FLOWS_RU.md](docs/MANUAL_TEST_FLOWS_RU.md)

Это AMM по математике Uniswap V2. Свопы и доказательства считаются на сервере, а токены всё время лежат в контракте-хранилище. Новый `ZkRubaVault` принимает новое состояние только вместе с Groth16-доказательством, а любое действие пользователя должно быть подписано его владельцем. В одном интерфейсе три пары: **RUBA / USDT**, **RUBA / WETH** и **WETH / WBTC**. У каждой пары свой Vault, свои балансы, LP-доли, регистрации, claims, журнал и ключ восстановления пула. Токены ERC20 общие, но депозит в один Vault другой не пополняет

Все четыре токена тестовые, это `DemoToken`: **Demo RUBA (18 знаков), Demo USDT (6), Demo WETH (18), Demo WBTC (8)**. WETH не оборачивает ETH, WBTC не связан с мостом из BTC, USDT не настоящий Tether. Считаем в целых числах с точностью токенов выбранной пары. Во внутреннем API имена `RUBA`/`USDT` просто значат token0/token1, а интерфейс и квитанции берут символы и точность из метаданных рынка

Адреса и проверенное состояние текущего выпуска в **Sepolia** лежат в [deployments/sepolia-v2.json](deployments/sepolia-v2.json). У него свой каталог `data/sepolia-partial-v2-20261123`, свой набор ZK-артефактов и локальный интерфейс **http://127.0.0.1:3005/**, который запускается командой `npm run sepolia:start`. Версии, резервы и статус в снимке актуальны на блок проверки, который там указан. Текущее состояние всегда читается из сети

Старый [deployments/sepolia.json](deployments/sepolia.json) оставили для истории: там другие адреса и каталог `data/sepolia`. В том выпуске тестовый кошелёк получил 10 000 RUBA, 10 000 USDT, 10 WETH и 1 WBTC, а бот сделал четыре сделки RUBA/USDT и сдвинул цену с 1 до 1,05 USDT за RUBA. Квитанция [sepolia-demo-disclosure.json](deployments/sepolia-demo-disclosure.json) тоже оттуда: она сверяется со старым Vault и к новым токенам и пулу отношения не имеет

23.11.2026 поменяли закрытие пакетов. Теперь в торговом пакете от 1 до 4 настоящих свопов. Четвёртый своп закрывает пакет сам, неполный пакет может закрыть админ, а ещё его закрывает запрос на вывод или снятие LP. Таймера нет. В текущем выпуске Sepolia новые verifier и Vault, старые контракты неизменяемые и работают по старым правилам. Подробнее и про допущения: [docs/PARTIAL_BATCHES.md](docs/PARTIAL_BATCHES.md)

25.11.2026 добавили допуск с согласием и KYC, три роли паузы, бота мониторинга, пересборку очереди и срок у подписи свопа. Всё это описано в [docs/RISK_CONTROLS_RU.md](docs/RISK_CONTROLS_RU.md)

Тогда же ужесточили допуск: без whitelist нельзя зарегистрироваться, внести депозит, делать свопы и добавлять ликвидность. Забрать свои LP-доли и вывести деньги можно и после отзыва допуска. Это касается только новых Vault. Старые контракты в Sepolia от обновления сервера или кода не меняются, базы и средства сами не переезжают. Каталог старого выпуска мы сохранили. Обойти проверку артефактов, переписав старый manifest, не получится: `sepolia:start` должен смотреть в каталог текущего выпуска

Архитектура нарисована на [доске RUBA в Miro](https://miro.com/app/board/uXjVENms6bs=/). Схема доказательства описана в [zk/SPEC.md](zk/SPEC.md), устройство трёх рынков в [docs/MULTI_MARKET.md](docs/MULTI_MARKET.md). **Для вывода не нужна подпись оператора.** Средства резервируются доказанным переходом kind6, после этого владелец сам забирает их по бессрочному claim. В текущем выпуске Vault с `withdrawalMode() = proven-reservation-v1` и отдельные базы. Интерфейс и ограничения описаны в [docs/PROVEN_WITHDRAWALS.md](docs/PROVEN_WITHDRAWALS.md) и [docs/DECISIONS.md](docs/DECISIONS.md). Полностью автономный prover и аварийный выход пока отложили

Кошельки подключаются через [Web3 Onboard](https://web3onboard.thirdweb.com/docs/modules/core) с модулем injected/EIP-6963. SDK собран локально в `ui/vendor/wallet-onboard.js`, так что CDN, API key и WalletConnect project ID не нужны. При подключении кошелёк ничего не подписывает: баланс обменника подгружается по кнопке «Загрузить мой баланс». «Отключить» работает даже во время ожидания подписи, незаконченный выбор кошелька можно отменить. Если меняли SDK или entry, пересоберите его через `npm run build:ui`. `npm run test:ui` тоже его собирает

## Быстрый запуск

Понадобятся Node.js **22.13+**, npm и Foundry (`forge`, `anvil`). Solidity 0.8.26 ставится из npm. Скрипт запуска сам выберет подходящий Node и проверит SQLite, флаг `--experimental-strip-types` не нужен. Проверить окружение: `npm run doctor`. Если Node лежит в нестандартном месте, укажите `RUBA_NODE_BINARY=/полный/путь/к/node`

```bash
npm ci
npm run zk:build
npm run dev
```

`zk:build` компилирует схему на Circom, делает тестовые proving и verifying keys, manifest в `zk/artifacts/` и `src/generated/Groth16Verifier.sol`. Всё это генерируется локально, поэтому после клонирования соберите артефакты до запуска и до полного прогона тестов. Первая сборка долгая, потому что в неё входит **локальный тестовый trusted setup**. Дальше используйте уже собранный набор, пересобирать нужно только после изменения схемы. Сервер сверяет хеши артефактов и байткод развёрнутых verifier и Poseidon. Если набор уже есть, `zk:build` можно пропустить. Если продолжаете старый план Sepolia, оставьте артефакты, которые в нём закреплены

У схемы `ruba-transition-v2` **13 public signals**. Все рынки используют одни и те же Groth16 verifier, Poseidon и набор публичных артефактов. Для сборки берём Powers of Tau `2^18`, а circuit-specific setup и вклад в него у нас локальные и тестовые. `manifest.json`, WASM, proving key, verification key и Solidity verifier должны быть из одного набора. Proving key публичный, это не приватный ключ кошелька

`npm run dev` (или `npm run markets:dev`) поднимает временный **Anvil с тремя рынками**: разворачивает четыре DemoToken, общие Groth16 verifier и Poseidon и три новых `ZkRubaVault`. Потом в каждом Vault регистрирует LP и бота, вносит их средства и публикует начальную ликвидность с доказательством:

| Рынок | Начальный пул | Свои средства бота |
| --- | --- | --- |
| `ruba-usdt` | 3 000 RUBA / 3 000 USDT | 3 000 RUBA / 3 000 USDT |
| `ruba-weth` | 3 000 RUBA / 1 WETH | 3 000 RUBA / 1 WETH |
| `weth-wbtc` | 3 WETH / 0,1 WBTC | 3 WETH / 0,1 WBTC |

Боты сначала выключены. Подготовку оплачивают локальные deployer и LP, у prover после неё нет ETH, и разрешения на публикацию он не подписывает. Когда всё поднимется, открывайте **http://127.0.0.1:3001/**. Другой порт: `PORT=3002 npm run dev`

В терминале будут RPC, Chain ID **31337**, адрес локального админа и тестовый ключ трейдера. Добавьте сеть в MetaMask или Rabby и импортируйте этот аккаунт. На нём уже есть тестовый ETH и допуск к регистрации, депозиту, SWAP и ADD_LP во всех трёх Vault, а ERC20 можно взять в кране прямо в интерфейсе. Ключ годится только для временной локальной сети. После Ctrl+C сеть и её журналы удаляются

| Страница | Что можно сделать |
| --- | --- |
| Вход | Галочка и «Продолжить» открывают разделы. Это просто подтверждение входа, допуск выдаётся отдельно в «Мой баланс» |
| Выбор рынка | RUBA/USDT, RUBA/WETH или WETH/WBTC, у каждого свой Vault и свой баланс |
| Обмен | Направление, сумма, минимальный результат, подпись заявки и отдельная публикация готового перехода |
| Цена и бот | График принятой цены AMM и ручного ориентира, статус бота. Настройки с подписью доступны админу |
| Ликвидность | Внести токены в пул, посмотреть LP-доли, вернуть доли на внутренний баланс |
| Мой баланс | Допуск с согласием и KYC, депозит, вывод, регистрация, proof баланса и backup с открытиями claims |
| Раскрытие (`/disclosure`) | Посмотреть квитанцию, которую человек передал сам, с солью и Merkle proof. Вход, кошелёк и роль не нужны |

Порядок такой: подтвердите вход, выберите рынок и подключите кошелёк. В «Мой баланс» возьмите тестовый токен в кране и внесите его в Vault выбранного рынка. Кран отправляет отдельную транзакцию в Ethereum и выдаёт токены **в кошелёк**, а не на внутренний баланс и не в LP. Выдача раз в 60 секунд на аккаунт и токен: 10 000 RUBA, 10 000 USDT, 10 WETH или 1 WBTC. ETH на газ кран не даёт. После депозита опубликуйте готовые контрольные переходы, и можно пробовать свопы и ликвидность

Чтобы зарегистрироваться и внести деньги, адрес должен быть в whitelist конкретного Vault. Для депозита ещё нужна принятая ZK-регистрация, интерфейс сам предложит её опубликовать. Допуск проверяется у владельца счёта, а не у того, кто платит за публикацию. Пауза рынка останавливает депозиты, свопы и добавление ликвидности, а регистрацию нет. Галочка на входе допуск не даёт. Если у рынка есть сервер допуска, участник подписывает согласие и номер KYC, получает разрешение и сам отправляет `admit` в Vault. Тестовому аккаунту допуск выдаёт скрипт подготовки. После отзыва допуска можно смотреть баланс, забрать свои LP-доли и вывести деньги. Депозиты, которые контракт уже принял, учитываются и после удаления из whitelist, иначе их нельзя было бы вывести

Если снять подтверждение входа или сменить сеть или аккаунт, операции снова блокируются. При смене рынка кошелёк остаётся подключён, а котировка, формы, балансы на экране и статус публикации сбрасываются. Сами деньги между Vault не переезжают, для этого нужно вывести из одного и внести в другой

Старое однорыночное ZK-демо RUBA/USDT с ликвидностью 1 000/1 000 запускается через `npm run zk:dev`. Это отдельная временная сеть, каталога трёх рынков там нет

Старый режим с доверенным сервером тоже остался: `npm run dev:legacy`. ZK он не проверяет. Старый Vault не превращается в ZK-vault после обновления сервера, для этого нужен новый контракт и подходящие артефакты

## Цены и бот

Публичный dashboard и синий график показывают только **принятый checkpoint**: цену AMM, резервы, stateVersion и блок. Первые 1-3 свопа, которые ещё ждут публикации, туда не попадают. Красная часть графика строится по вашей же квитанции: это ваш личный расчёт до и после обмена, а не новая публичная цена

Ориентиры цены админ задаёт руками. По умолчанию RUBA=1, USDT=1, WETH=3 000, WBTC=90 000 USDT, а USDT всегда равен 1. Ориентир для пары считается как отношение этих цен с учётом decimals. Никаких внешних бирж и оракулов мы не опрашиваем, это демо, а не реальные котировки

Менять ориентиры, включать бота и запрашивать приватный monitor может кошелёк `admin` из каталога `/markets` и manifest. Локально это deployer Anvil, в Sepolia отдельный deployer. Панель админа просит подпись EIP-712 `RubaMarketControl` с одноразовым control nonce и сроком до 600 секунд, приватный ключ по HTTP никуда не уходит. Цены общие для всех рынков, а включение бота и его задержка настраиваются для каждого пула. Это подпись сообщения для настроек сервера, а не транзакция, газ нужен только для вызовов ERC20 и Vault и для сделок бота

Кнопка приватного monitor показывает текущие резервы и цену на сервере, включая ещё не принятые действия. Ответ помечен `private-current`, требует подписи админа и публичный график не меняет

Бот по умолчанию выключен. Задержка по умолчанию 30 секунд, можно поставить от 5 до 3 600. После сделок или смены ориентира бот ждёт эту задержку и делает корректирующие свопы только на свои средства в выбранном Vault. Он подтягивает цену к ручному ориентиру, это не треугольный арбитраж между тремя пулами. По публичным настройкам его план не узнать

В торговом пакете максимум четыре свопа. Бот считает корректирующие свопы, пока есть свободные места, но админ или запрос на выход могут закрыть пакет раньше. Если объём слишком маленький, не хватает средств или мешает что-то ещё, бот показывает ожидание, так что включённый бот не обязательно доведёт хвост из 1-3 сделок до конца. Готовые proof бот публикует за свой ETH. Если его выключить, новых операций не будет, но уже отправленную транзакцию это не отменит

## Запуск в Sepolia

Команды работают только с тестовой сетью **Sepolia, Chain ID 11155111**. Это отдельное развёртывание, а не обновление локального Anvil или Tenderly. Если есть ключ или готовый manifest, это ещё не значит, что контракты развёрнуты: когда не хватает тестового ETH, план просто сохраняется, и его можно продолжить

Если `.env.sepolia` ещё нет, скопируйте пример:

```bash
cp .env.sepolia.example .env.sepolia
```

Настройки в `.env.sepolia` такие же, как в примере:

```dotenv
SEPOLIA_RPC_URL=https://ethereum-sepolia-rpc.publicnode.com
SEPOLIA_STATE_DIR=data/sepolia-partial-v2-20261123
ZK_ARTIFACTS_DIR=zk/artifacts
PORT=3005
SEPOLIA_CONFIRMATIONS=1
SEPOLIA_TEST_WALLET=
# Необязательные верхние границы, целые числа в wei:
# SEPOLIA_MAX_FEE_PER_GAS_WEI=100000000
# SEPOLIA_MAX_TOTAL_FEE_WEI=30000000000000000
```

Укажите свой HTTPS RPC и публичный адрес тестового кошелька в `SEPOLIA_TEST_WALLET`. `sepolia:prepare` и `sepolia:deploy` запишут его в `manifest.roles.testWallet`, а bootstrap даст ему допуск к регистрации, депозиту, SWAP и ADD_LP во всех трёх Vault. Регистрацию, кран и депозит пользователь делает сам

Адрес можно добавить и потом, после подготовки или даже после развёртывания. Поменяйте `SEPOLIA_TEST_WALLET`, запустите `sepolia:prepare`, потом снова `sepolia:deploy` с тем же каталогом и достаточным бюджетом на газ. Новые транзакции whitelist допишутся в журнал, а уже сделанные шаги bootstrap не повторятся. Старые разрешённые кошельки остаются в `roles.authorizedTestWallets`: если поменять настройку, допуск у них молча не пропадёт. Чтобы его отозвать, админ сам вызывает `setWhitelist(address,false)` в нужных Vault

Кошелёк deployer лежит в `<SEPOLIA_STATE_DIR>/deployer.json`. Скрипты берут его из выбранного `SEPOLIA_STATE_DIR`, поэтому не заменяйте этот файл, если продолжаете развёртывание. В нём секретный ключ. Там же, с закрытыми правами доступа, лежат ключи LP, бота и prover, три разных pool recovery key, SQLite и журнал подписанных транзакций. В архивы с исходниками и в публичный manifest они не попадают. В manifest есть только адреса и хеши транзакций, приватные ключи в лог не пишутся

**Админ сайта - это `deployer.address` из этого файла.** Чтобы открыть панель управления, подключите в браузере именно этот аккаунт, при необходимости импортируйте его ключ в кошелёк у себя на компьютере. В само приложение и в HTTP-запросы ключ вводить не нужно. `SEPOLIA_TEST_WALLET` получает только допуск к торговле, админом он не становится. LP, бот и prover - отдельные роли: начальная ликвидность, свои корректирующие сделки и подготовка доказательств. Прав админа у prover нет

```bash
npm run sepolia:prepare
```

Эта команда **ничего не отправляет в сеть**. Она проверяет сеть и артефакты, сохраняет `<SEPOLIA_STATE_DIR>/manifest.json`, показывает адрес deployer, его баланс и сколько примерно нужно на развёртывание, bootstrap и газ для LP и бота. Для зависимостей, которые ещё не развёрнуты, в оценке могут стоять помеченные заглушки, это не реальная цена в Sepolia. Если баланса не хватает, пополните показанный адрес тестовым **Sepolia ETH** и запустите `sepolia:prepare` ещё раз. Не берите сумму ETH с потолка, ориентируйтесь на свежую оценку от RPC

Когда денег хватает:

```bash
npm run sepolia:deploy
npm run sepolia:start
```

`sepolia:deploy` отправляет настоящие транзакции в тестовую сеть: разворачивает четыре токена, общие verifier и Poseidon и три Vault, настраивает роли, доказывает регистрации, пополняет LP и бота и публикует начальную ликвидность. Всё готово, когда **`manifest.status = ready`** и сходятся receipts, байткоды и принятые roots. Если не хватило денег или процесс прервался, просто запустите ту же команду с тем же каталогом: сохранённые nonce, подписанные bytes и хеши позволяют продолжить с того же места. Если nonce конфликтует, артефакты чужие или потерялась рабочая база, продолжение блокируется

Газ в Sepolia оцениваем по текущему RPC, с учётом создания новых аккаунтов, поэтому для переводов LP и боту фиксированный лимит 21 000 не используется. Если частичное развёртывание упёрлось в старый общий потолок, остановите deploy, задайте `SEPOLIA_MAX_TOTAL_FEE_WEI` и пересчитайте оставшиеся операции. Verifier и Poseidon к этому моменту уже должны быть подтверждены:

```bash
npm run sepolia:budget -- --out data/sepolia-partial-v2-20261123/budget-proposal.json
npm run sepolia:budget -- --apply data/sepolia-partial-v2-20261123/budget-proposal.json
npm run sepolia:deploy
```

Preview план не меняет. Apply ещё раз проверяет расчёт, receipts, свободные nonce, баланс и общий лимит и сохраняет новую версию бюджета. Подписанные bytes, комиссии, суммы пополнения и сделанные шаги остаются как были. `carriedSetupReserveGas` - это отдельный запас, а не замер RPC, операции без оценки перечислены в `unestimatedSetupIds`. Одновременно запустить deploy, prepare и apply не получится, их разводит общий lock

`sepolia:start` запускает уже подготовленные рынки, `.env.sepolia` все команды Sepolia подхватывают сами. С настройками выше интерфейс откроется на **http://127.0.0.1:3005/**. Добавьте Sepolia в кошелёк и импортируйте DemoToken по адресам из manifest. Пользователю нужен свой Sepolia ETH на кран, approve, депозит, публикации и выплаты, кран газ не пополняет. Чтобы бот работал без перерывов, у его адреса тоже должен быть ETH и свои средства в каждом включённом рынке

`SEPOLIA_CONFIRMATIONS=1` - это наша настройка подтверждений для тестового демо, к финальности mainnet она отношения не имеет. В остальных публичных режимах проверка финальности остаётся, а если найдена реорганизация, работа останавливается. Локальный trusted setup и это развёртывание не дают права говорить о безопасности для production или о прибыльности бота

## Как проходит операция

1. Браузер собирает параметры и сам считает commitment. Кошелёк подписывает EIP-712 `PrivateOperation(uint256 commitment)` в домене `RubaZkOperation` версии `2`, привязанном к chain ID и Vault. Своп и ADD_LP подписываются как `TimedPrivateOperation(uint256 commitment,uint256 deadline)` со сроком на час, после срока Vault их не примет. Это подпись сообщения, транзакция на этом шаге не отправляется
2. Сервер проверяет заявку, считает AMM или LP и одним действием сохраняет в SQLite новое предварительное состояние, подпись и witness. HTTP action nonce у нас отдельный и с `spendNonce` аккаунта не смешивается
3. Контрольный переход (`mode=0`) - это регистрация, депозиты, LP или учёт выплат без свопов. В торговом (`mode=1`) **от одного до четырёх** свопов. Четвёртый закрывает пакет сам, хвост из 1-3 закрывает админ или запрос на вывод или снятие LP. Скользящих окон нет
4. Prover строит настоящее доказательство Groth16. Оно связывает старое и новое дерево аккаунтов, пул, nonce, вводы и выплаты, формулу, округления, квитанции в дереве на четыре места и опубликованные зашифрованные обновления
5. Сервер отдаёт готовый вызов `publishProvenTransition`: 13 public signals, восемь записей metadata и DA, pool DA и proof. Разрешения, подписи, срока и epoch оператора в нём нет, верному proof они не нужны
6. Отправить этот вызов может кто угодно, со своего кошелька и за свой газ. Контракт проверяет подписи владельцев, proof, порядок версий и корней и canonical inbox и только потом принимает root. Обычный sync worker просто следит за сетью и ничего не отправляет. Включённый бот может платить за публикации со своего кошелька
7. Когда сверка с Vault прошла, интерфейс показывает принятое состояние. Если отказаться от публикации в кошельке, заявка на сервере всё равно остаётся, опубликовать её можно потом отдельной кнопкой

В торговый переход входят расчёты 1-4 свопов. Хвост из 1-3 админ может закрыть кнопкой «Закрыть текущий пакет» в выбранном рынке, вывод или снятие LP тоже закрывают хвост, не дожидаясь четвёртого свопа. Подпись админа разрешает закрыть пакет на сервере, а потом кошелёк отдельно публикует proof и платит за газ. Аварийного выхода нет. Хвост с подписью со сроком сервер закрывает сам за 20 минут до срока. Если в это время ждут свопы, контрольные операции попадают в тот же переход. Когда места в нём нет, новые действия блокируются, но уже принятые не теряются. Без работающего prover публиковать нечего

## Как выводятся деньги

Пользователь подписывает kind6 с `nonce == oldSpendNonce`. Proof переносит сумму из доступного баланса в pending, а принятый commitment даёт владельцу бессрочное право на одну выплату. Если переход готов, интерфейс может сразу опубликовать его и выплатить деньги одной транзакцией через `publishProvenTransitionAndWithdraw`. Если claim уже принят, его можно погасить отдельным `withdrawProven`, даже после новых roots, долгого ожидания или смены оператора

Для открытия нужны `account, token, amount, nonce, spendNonce, salt`. Контракт пересчитывает commitment, проверяет, что это владелец и что claim ещё не потрачен, и переводит токены только ему. Открытие сохраняется в браузере ещё до запроса на сервер и подписи в кошельке: если ответ потерялся или пользователь отказался, повторно резервировать деньги интерфейс не предложит. Если перед выводом ждут 1-3 свопа, запрос на вывод закрывает этот хвост. Интерфейс публикует нужные переходы и резервирование, не дожидаясь четвёртого свопа, таймера у неполного пакета нет. Если пакет не проходит из-за паузы, отзыва допуска или истёкшего срока подписи, админ пересобирает очередь: сервер убирает операции, которые Vault отклонит, и собирает переход заново из остальных, см. [docs/RISK_CONTROLS_RU.md](docs/RISK_CONTROLS_RU.md)

После выплаты canonical kind7 следующим переходом уменьшает pending и custody. Kind8 REFUND и старый вывод по подписи запрещены: нельзя одновременно вернуть резерв в available и оставить право на выплату. Whitelist и пауза рынка погашению claim не мешают, а пауза выплат конкретного токена работает как раньше

## Что доказывается и что видно снаружи

Ограничения MVP **для каждого Vault**: **16 аккаунтов**, глубина Merkle-дерева **4**, до **8 операций** в одном переходе. Балансы, суммы, резервы, custody и LP-доли влезают в `uint96`, а nonce, inbox cursor и trade IDs в `uint64`. Всё, что больше, отклоняется. Поле BN254, недопустимый корень по модулю не приводится. Ещё контракт ограничивает отдельный депозит и общий inbox exposure по каждому токену значением `2^96 - 1`. Считаются все принятые депозиты, в том числе те, что prover ещё не обработал, минус уже сделанные выплаты. Если перевести ERC-20 напрямую, мимо `deposit`, баланс пользователя не появится и в этот счётчик перевод не войдёт

В листе аккаунта лежат владелец, два доступных баланса, LP-доли, nonce, два ожидающих вывода, commitment ключа восстановления и соль. `accountsRoot` фиксирует все 16 листьев, а `poolHash` фиксирует резервы, supply и заблокированные LP-доли и custody

```text
stateRoot = PoseidonFold(domain, accountsRoot, poolHash,
                         inboxCursor, nextTradeId, poolKeyCommit)
```

Начальное состояние - пустое дерево аккаунтов, пустой пул, cursor 0 и nextTradeId 1, его считает сам контракт. И контрольные, и торговые переходы продолжают одну цепочку `stateVersion` и root. В ZK-vault старые `publishBatch`, `publishSignedBatch` и `publishZkTransition` с шестью параметрами отключены: новый корень принимается только с proof, разрешение оператора не используется

При свопе вход уходит из доступного баланса в резерв, а выход из другого резерва попадает на доступный баланс владельца. Сами ERC-20 всё время лежат в Vault, а полученный баланс в следующем обмене как резерв не участвует. Комиссия 0,3% остаётся в пуле. Ввод и вывод ликвидности считаются по математике V2, первые 1 000 минимальных LP-долей блокируются навсегда. LP-доли пока не ERC-20

Публично видны **адреса владельцев операций, изменённые слоты, виды операций, кто платил за газ, вводы и выплаты, корни, proof и зашифрованные DA**. Депозиты и выплаты видны вместе с суммами. Суммы обменов и операций с ликвидностью открытым текстом не публикуются, но сервер и prover их видят и знают viewing keys. Анонимности владельца, скрытия метаданных и защиты от анализа по времени мы не обещаем. В демо публичный dashboard к тому же показывает принятые резервы и цену пула. По их изменениям, времени публикаций и вводам и выплатам можно примерно оценить объёмы сделок, пакеты по четыре сделки анонимность не гарантируют

Каждый торговый переход даёт `receiptsRoot` дерева на четыре квитанции Poseidon v2: от одной до четырёх настоящих, остальные нулевые. Для настоящей квитанции proof состоит из двух соседних хешей, нулевое место за сделку выдать нельзя. Схема связывает квитанции с реальными свопами. Старые квитанции на Keccak раскрываются отдельно, как исторический формат. Одного Merkle proof мало, нужно ещё убедиться, что сам ZK-переход принят

## Восстановление баланса без Web2

Каждая принятая операция кладёт в calldata новый хеш листа аккаунта и семь зашифрованных полей. Последний poolHash и шесть зашифрованных полей пула тоже лежат в calldata. Proof связывает шифротекст с доказанным состоянием, так что ссылки на сервер, CID или пометки `published` для восстановления недостаточно

`zk/recovery.js` работает и в браузере, и в Node, сервер ему не нужен. Он фиксирует блок RPC, читает `ZkTransitionPublished`, успешные receipts и calldata, сверяет `transitions(version)`, хеши auth и DA и всю цепочку от пустого начального состояния. По всем изменениям восстанавливает 16 хешей листьев и Merkle path **на выбранный блок**. Своим ключом восстановления можно расшифровать баланс, nonce, LP-доли и ожидающие выплаты и проверить commitment листа и ключа. Чужие балансы своим ключом не восстановить

Кнопка «Восстановить баланс из блокчейна» ничего не отправляет и к серверу не обращается. Нужны сеть, адрес Vault, RPC с историей logs и calldata и свой ключ восстановления. В локальном MVP поддержаны прямые транзакции `publishProvenTransition` и `publishProvenTransitionAndWithdraw`, старые `publishZkTransition` тоже читаются для прежнего развёртывания. Вызовы через multicall потребовали бы traces, поэтому их не поддерживаем. RPC мы доверяем, light client это не заменяет

Файл `ruba-zk-account-backup` версии `2` содержит chain, Vault, владельца и slot, **ключ восстановления**, keyCommit, account, path, accountsRoot, poolHash, stateRoot, cursors, poolKeyCommit, stateVersion и привязку к блоку и транзакции. Храните его как секрет от своего баланса, отдельно от файла раскрытия одной сделки. При импорте проверяются формат и хеши, сохранённые подписи никуда не отправляются. Пометка о принятии внутри файла доказательством не считается: без независимой сверки это `snapshot-only`, а корректный, но старый снимок помечается `historical`, а не как текущий баланс. Чтобы убедиться, что его старый root действительно принимался, нужно отдельно прочитать `transitions(version)`. Неопубликованные 1-3 свопа по цепочке не восстановить, в принятом состоянии их ещё нет

Одного восстановленного баланса и proof **для выплаты мало**: нужны сохранённые открытия `withdrawalClaims[]` с amount, nonce и salt. В шифротексте аккаунта только общая сумма pending, потерянное открытие по нему не восстановить. Каждое открытие сохраняется до запроса на сервер и подписи в кошельке и попадает в backup. Импорт проверяет commitment, domain, владельца и slot, но ничего не отправляет. Флаги accepted и spent берутся из Vault, а не из файла. Если claim уже принят, владелец может сам вызвать `withdrawProven`, без сервера и оператора. Новые proof без работающего prover и аварийный выход отложены, см. [docs/DECISIONS.md](docs/DECISIONS.md). Чтобы восстановить весь сервер, нужен согласованный backup SQLite и секреты пула и аккаунтов, ключ одного владельца весь рынок не вернёт. Backup, открытия и их локальный кеш привязаны к chain ID, адресу конкретного Vault и владельцу, данные разных рынков по символу токена не смешиваются

## HTTP и раскрытие

API и интерфейс слушают только loopback: локальное демо обычно на `127.0.0.1:3001`, Sepolia с настройками из примера на `127.0.0.1:3005`. Ethers и crypto раздаются локально. Три постоянных рынка запускаются через `sepolia:start` с сохранёнными manifest, ключами ролей и отдельными SQLite. Однорыночный `npm start` с `.env` тоже работает, но ему нужен адрес **нового** ZK-vault, `PROOF_MODE=zk`, артефакты, блок развёртывания и локальные настройки prover и recovery. Подпись админа для публикации верного proof не нужна. Если vault не тот, verifier или Poseidon другие, цепочка разорвана или журнал потерян, сервер не откатывается тихо на доверенные корни

| Путь | Зачем |
| --- | --- |
| `GET /markets` | Каталог трёх рынков, метаданные токенов и публичные параметры управления |
| `GET /markets/:marketId/dashboard` | Принятый checkpoint, история цен, ручные ориентиры и статус бота |
| `GET /markets/:marketId/config` | Адреса Vault, режим и типы подписей, без witness и ключей восстановления |
| `GET /markets/:marketId/nonce?account=0x...` | HTTP action nonce владельца в этом рынке |
| `GET /markets/:marketId/publication` | Самый ранний готовый переход рынка для отправки или статус ожидания |
| `POST /markets/:marketId/actions` | Подписанные операции, свой баланс и proof, приватные квитанции |
| `GET /markets/:marketId/disclosure/batches/:id` | Публичные поля пакета и сверка с нужным Vault |
| `POST /admin/action` | Ручные цены с подписью, настройка бота, приватный monitor и `closeBatch` выбранного рынка |
| `/disclosure` | Просмотр загруженного JSON, вход и кошелёк не нужны |

Корневые `/config`, `/nonce`, `/actions`, `/publication` и `/disclosure/batches/:id` остались как синонимы для рынка по умолчанию `ruba-usdt`. Просмотрщик квитанций выбирает рынок по **chain ID и Vault**, а не по `marketId` из файла, которому нельзя доверять: одинаковые tradeId и batchId в разных рынках не делают квитанции взаимозаменяемыми

Суммы и идентификаторы в JSON передаются строками, а не числами JavaScript. Квитанция становится полной, только когда закрыт пакет из четырёх, до этого proof для неё нет. Статус `published` проверяется чтением контракта, а не флагом в базе сервера. Раскрытие показывает направление, суммы, соль и proof только из того файла, который вам передали. Публичной истории чужих сделок нет

## Старый запуск на Tenderly

Этот раздел про прежний MVP с доверенным сервером и `RubaVault`, а не про ZK. Форки Tenderly и их развёртывания мы в этой версии не трогали и не тестировали. Новую ZK-версию запускайте на локальном Anvil или в Sepolia, как описано выше

Создайте в Tenderly **Virtual TestNet на основе Ethereum mainnet** со своим Custom Chain ID, например `73571`, только не `1`. Понадобятся **Admin RPC**, публичный адрес вашего кошелька и лучше ещё **Public RPC того же форка** для MetaMask или Rabby. Приватный ключ кошелька проекту не нужен

Если сейчас запущен `npm run dev`, остановите его через Ctrl+C. Потом:

```bash
npm run tenderly
```

Откройте **http://127.0.0.1:3001/setup**, файл `.env` для этого не нужен. Если порт занят, запустите `PORT=3002 npm run tenderly` и откройте адрес с портом `3002`

1. Вставьте в форму Admin RPC, Public RPC и адрес кошелька
2. Нажмите **«Подготовить и запустить»** и дождитесь, пока пройдут все шаги
3. Добавьте в MetaMask или Rabby сеть с Public RPC этого форка, показанным Chain ID и валютой ETH. Импортируйте токены по адресам со страницы
4. Нажмите **«Открыть обмен»**, подтвердите вход и подключите кошелёк
5. В «Мой баланс» переведите токены с кошелька на внутренний баланс. После этого можно меняться и добавлять ликвидность

Что делает подготовка по умолчанию:

| Действие | Результат |
| --- | --- |
| Развёртывание | Тестовый RUBA с 18 знаками и новый `RubaVault` |
| USDT | Настоящий контракт USDT из Ethereum `0xdAC17F958D2ee523a2206206994597C13D831ec7`, 6 знаков, в состоянии форка |
| Допуск | Указанный кошелёк добавлен в whitelist vault |
| Деньги на кошельке | Не меньше 10 ETH на газ, 10 000 RUBA и 10 000 USDT |
| Начальная ликвидность | 1 000 RUBA / 1 000 USDT вносятся в vault прямо в транзакции подготовки, индексатор видит оба депозита и зачисляет их в пул на сервере |

USDT и ETH выдаёт сам Tenderly внутри виртуальной сети, RUBA выпускает тестовый контракт. Суммы для кошелька и начального пула можно поменять в дополнительных настройках формы. AMM, внутренние балансы и LP-доли считаются на сервере, а vault хранит токены, следит за вводами и выплатами и фиксирует корни пакетов

### Сколько транзакций уходит на подготовку

Для нового форка вся подготовка помещается в одну транзакцию развёртывания: внутри неё создаются RUBA и vault, выдаются деньги, настраивается whitelist, даются разрешения и вносятся оба депозита ликвидности. Для этого используется атомарная выдача средств Tenderly из Solidity. Ещё одна операция через Admin RPC пополняет ETH у deployer, чтобы он мог отправить эту транзакцию

| Режим развёртывания | Операций, меняющих состояние | Остаток из лимита 20 |
| --- | ---: | ---: |
| Атомарная подготовка Tenderly | 2 | 18 |
| Запасной вариант без cheatcodes в Solidity, стандартные суммы ETH | 3 | 17 |
| Запасной вариант со своей суммой ETH для кошелька | До 4 | Не меньше 16 |

Режим выбирается до отправки транзакций и показывается в ходе подготовки. Внутренние вызовы одной транзакции отдельными отправками не считаются. Если просто упаковать несколько JSON-RPC запросов в один, расход не уменьшится. Чтения RPC, оценка газа и другие лимиты Tenderly считаются отдельно. Квота, уже потраченная на существующий форк, после обновления не возвращается

Настройки формы сохраняются в `data/tenderly-ui.json`, а контракты, тестовые ключи сервера и журнал SQLite привязаны к RPC и лежат в `data/tenderly/`. Ctrl+C останавливает интерфейс, форк и журнал остаются. В следующий раз после `npm run tenderly` нажмите **«Запустить предыдущий форк»**, и подхватится сохранённое развёртывание. При повторном запуске атомарного развёртывания с тем же кошельком **новых транзакций 0**: потраченные деньги сами не возвращаются, пул остаётся как был. Чтобы пополнить кошелёк, есть `npm run tenderly:fund`: в атомарном режиме это одна транзакция, в запасном до трёх операций. Начальная ликвидность второй раз не добавляется. Старые развёртывания остаются со своими адресами и старой схемой подготовки, скрипт сам их на новые контракты не заменит. Admin RPC не показывается ни в результатах настройки, ни в публичной конфигурации обмена, для кошелька берите Public RPC. В `data/` лежат секреты сервера, выкладывать эту папку нельзя

### Настройка через файлы

Вместо формы можно скопировать `.env.tenderly.example` в `.env.tenderly` и заполнить:

```dotenv
TENDERLY_RPC_URL=https://virtual.mainnet.eu.rpc.tenderly.co/ВАШ_ADMIN_RPC
TENDERLY_PUBLIC_RPC_URL=https://virtual.mainnet.eu.rpc.tenderly.co/ВАШ_PUBLIC_RPC
TEST_WALLET_ADDRESS=0xВАШ_ПУБЛИЧНЫЙ_АДРЕС
```

Или оставьте `TENDERLY_RPC_URL` пустым и пропишите Admin RPC в `foundry.toml`:

```toml
[rpc_endpoints]
mainnet = "https://virtual.mainnet.eu.rpc.tenderly.co/ВАШ_ADMIN_RPC"
```

По умолчанию берётся alias `mainnet`, другой можно выбрать через `TENDERLY_RPC_ENDPOINT`. В `foundry.toml` уже есть `mainnet = "${TENDERLY_RPC_URL}"`, так что если `.env.tenderly` заполнен, TOML трогать не надо. В `.env.tenderly` можно ещё задать суммы `TENDERLY_WALLET_ETH`, `TENDERLY_WALLET_RUBA`, `TENDERLY_WALLET_USDT`, `TENDERLY_SEED_RUBA`, `TENDERLY_SEED_USDT` и `PORT`

| Команда | Что делает |
| --- | --- |
| `npm run tenderly` | Открывает страницу настройки и запускает всё через форму |
| `npm run tenderly:setup` | Готовит форк по `.env.tenderly` или alias Foundry, HTTP не поднимает |
| `npm run tenderly:direct` | Готовит или продолжает по файлам и сразу запускает обмен, без страницы настройки |
| `npm run tenderly:fund` | Пополняет кошелёк до заданных сумм в уже готовом форке |
| `npm run test:tenderly` | Живой тест форка с отдельным тестовым кошельком, отправляет транзакции и меняет состояние форка |

Перед `tenderly:setup`, `tenderly:direct`, `tenderly:fund` и живым тестом остановите запущенный экземпляр этого рынка: два процесса одновременно с одним журналом работать не дадут. Для нового форка нужен новый RPC. Если форк сбросили или у опубликованных сделок потерялся журнал, продолжить не получится

В режиме Tenderly сервер принимает новые виртуальные блоки, не дожидаясь финальности, как в mainnet. Обычный запуск API по-прежнему ждёт финализированных блоков. Документация Tenderly: [Admin RPC](https://docs.tenderly.co/virtual-environments/admin-rpc), [адреса Admin и Public RPC](https://docs.tenderly.co/virtual-environments/named-rpc-urls), [атомарные cheatcodes в Solidity](https://docs.tenderly.co/virtual-environments/precompiles)
