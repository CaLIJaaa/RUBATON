# RUBA ZK MVP v2: how the circuit and the Vault fit together

These are our notes on how Circom v2 and the proof-only Vault work together. The withdrawal protocol itself is described in docs/PROVEN_WITHDRAWALS.md: kind6 signed by the owner creates a perpetual onchain claim that is redeemed without any operator permit. Proving without the server and an emergency exit are postponed. Older v2 deployments used operator authorized publication and withdrawal, the recovery scanner can still read them, but don't confuse them with the new withdrawal mode. Old tests and contracts are still in the repo, but the ZK app always deploys ZkRubaVault and requires real Groth16 proofs

## Bounds and cryptography

- BN254 scalar field Fr = 21888242871839275222246405745257275088548364400416034343698204186575808495617
- Circom 2, circomlib Poseidon(2) and snarkjs Groth16. The trusted setup is local and for testing only
- 16 accounts, Merkle depth 4; maximum 8 economic operations per transition
- Balances, amounts, reserves, shares and custody: unsigned 96 bits. Nonces/trade IDs/cursors: 64 bits
- The Vault rejects any deposit above `2^96-1`, and also rejects deposits once the total canonical inbox exposure for a token would go above that, counting deposits no proof has consumed yet. Payouts reduce the exposure (it never goes below zero, so legacy withdrawals keep working). ERC-20 sent to the Vault directly does not create credit and does not count here
- Every integer division is constrained with positive denominator and bounded remainder
- H(a,b)=circomlib Poseidon(2). fold(tag,values) starts at tag and applies H(acc,value)
- Tags: DOMAIN=101, ACCOUNT=102, POOL=103, STATE=104, OP=105, AUTH=106, DA=107, RECEIPT=108, KEY=109, STREAM=110
- All roots are field-native bytes32; reject out-of-field values, never reduce public roots modulo Fr
- domain=fold(DOMAIN,[2,chainId,vault,ruba,usdt,poolKeyCommit])

## State

An account is exactly 9 fields: `[owner,ruba,usdt,shares,spendNonce,pendingRuba,pendingUsdt,recoveryKeyCommit,salt]`. Empty account has all fields zero. leaf=fold(ACCOUNT,[slot,...account]). Merkle parents are H(left,right) in this order, pairs are not sorted. Account owner and recoveryKeyCommit remain immutable after registration. Pool preimage: `[reserveRuba,reserveUsdt,totalSupply,lockedLiquidity,custodyRuba,custodyUsdt]`. poolHash=fold(POOL,pool). stateRoot=fold(STATE,[domain,accountsRoot,poolHash,inboxCursor,nextTradeId,poolKeyCommit]). Genesis is the empty tree, an empty pool, cursor 0 and nextTradeId=1. The contract computes it, the operator can't set it. The nonce used for API authentication is not spendNonce and is never part of this state

## Operations (ordered, padded to 8)

Kinds: 0 NOP, 1 REGISTER, 2 DEPOSIT, 3 SWAP, 4 ADD_LP, 5 REMOVE_LP, 6 RESERVE_WITHDRAWAL, 7 SETTLE_WITHDRAWAL, 8 REFUND_WITHDRAWAL

Private parameters `[p0,p1,p2,p3]`:

- REGISTER: `[recoveryKeyCommit,0,0,0]`; old account empty, new owner set, balances zero, nonce 1
- DEPOSIT: `[token,amount,eventId,depositId]`; credit available/custody, nonce unchanged
- SWAP: `[tokenIn,amountIn,minOut,0]`; V2 fee997/1000 exact floor; reserves/account change; nonce+1
- ADD_LP: `[rubaDesired,usdtDesired,rubaMin,usdtMin]`; existing V2 ratio/min mint; first mint uses floor sqrt, locks1000 shares; nonce+1
- REMOVE_LP: `[shares,rubaMin,usdtMin,0]`; exact floor redemptions to available; nonce+1
- RESERVE_WITHDRAWAL: `[token,amount,withdrawalNonce,0]`; available->pending; nonce+1. For the new Vault, withdrawalNonce must equal the account oldSpendNonce; an opening binds both equal uint64 nonces, amount and nonzero salt to this owner commitment
- SETTLE_WITHDRAWAL: `[token,amount,eventId,withdrawalNonce]`; pending/custody decrease; nonce unchanged
- REFUND_WITHDRAWAL: historical Circom v2 support for `[token,amount,withdrawalNonce,0]`; pending->available, nonce unchanged. FORBIDDEN by the new Vault, engine and API, because an accepted perpetual claim cannot safely coexist with refunding its reserved balance

Each operation changes one account leaf, plus the pool, cursor and trade counter. inboxCursor moves only on real bridge events, one at a time. REGISTER, SWAP, ADD, REMOVE and RESERVE need the user's EIP-712 signature. The old REFUND was signed by the operator, and the new proof-only publication rejects kind8 completely. DEPOSIT and SETTLE need no extra signature because the contract ties them to its own inbox

commitment=fold(OP,[domain,kind,slot,owner,oldSpendNonce,p0,p1,p2,p3,newSalt]). Typed authorization: domain `{name:RubaZkOperation,version:2,chainId,verifyingContract:vault}`; primary type `PrivateOperation(uint256 commitment)`. Registration uses the same authorization. There is no separate expiry. The HTTP Action deadline only limits the first submission, after that the one-time spendNonce signature has to stay publishable while its batch is still open. Cancelling on the server does not revoke the signature. The new publishProvenTransition ticket requires no operator permit, deadline or epoch. Historical publishZkTransition tickets used a separate expiring operator authorization; the new Vault disables that entry point. Old fields kept for wire compatibility never authorize a new call. The browser computes the commitment itself and never signs an opaque value from the server. The server and prover see recovery and viewing keys and plaintext, but never wallet signing keys. Owner addresses and changed slots are public, amounts stay hidden

## Circuit inputs and public signals

Public signals, exact order (13): `[domain,stateVersion,mode,previousRoot,newRoot,previousInboxCursor,newInboxCursor, previousTradeId,newTradeId,receiptsRoot,authDigest,daDigest,poolKeyCommit]`. previousTradeId and newTradeId are nextTradeId from the state (starting at 1), not the last used ID. Mode 0 is a control transition with no swaps and at least one operation, mode 1 is a trade with 1-4 real swaps. Circuit requires IsZero(swapCount) == 1-mode and swapCount <= 4. newTradeId-previousTradeId equals the actual swap count. Receipt trees retain four leaves, zero-padding absent positions; proofs outside the actual tradeCount are invalid. Every transition shares one stateVersion/root chain. Trade batch ID increments only for mode1. Control transitions must be proven too; no legacy setters or trusted root reseeding. The fourth swap automatically seals a trade packet. Authenticated administrator closeBatch and REMOVE_LP/RESERVE_WITHDRAWAL requests also seal a 1..3-swap tail. There is no timer. Other operations keep the journal order and the limit of 8 operations, and if needed the earlier batch is sealed before the exit is recorded. A manual close of an empty queue creates no new transition. Already sealed packets are not amended; the next publication always extends the accepted root chain. Trade batch IDs count trade packets, not floor((nextTradeId-1)/4)

The exact private witness fields are defined in zk/schema.ts, that file is the typed source of truth. The witness carries the starting pool and accounts root, every old account and its path, params, recovery keys and new salt, operation metadata, encrypted DA and four receipt slots (1-4 real ones for a trade batch, zeros for the rest). All final values are constrained

Public metadata for each operation goes into calldata and is committed by authDigest, NOP records are all zero: `{kind,slot,owner,commitment,eventId,token,amount,reference,signature}`. AUTH digest = fold(AUTH,[domain,stateVersion,...flatten each record excluding signature]) in record order: kind,slot,owner,commitment,eventId,token,amount,reference. For user/refund metadata eventId/token/amount/reference are zero; only private commitment reveals the private parameters to the proof. For bridge records fields match canonical inbox exactly; circuit enforces parameter equality with these metadata fields. Solidity checks user signatures (for the old refund, the current operator) and computes authDigest itself

## Canonical inbox and proven withdrawal

The new ZkRubaVault exposes withdrawalMode() = "proven-reservation-v1" and uses a fresh DB/deployment; old pending claims are not automatically migrated. The 13-signal format remains v2, but the 1..4-swap rule changes circuit constraints and requires new WASM, proving/verifying keys, verifier and Vault deployment. Since 2026-11-23 REGISTER and new deposits need the whitelist too, not only SWAP and ADD_LP. These checks are in the new Vault, old immutable deployments can't get them from a server or UI update. A new Vault is deployed without resetting or migrating existing databases, balances or claims. For successful kind6, the accepted header records commitment -> (owner,slot,stateVersion). The opening is (account,token,amount,nonce,spendNonce,salt), with uint96 positive amount, uint64 nonce == spendNonce == oldSpendNonce and nonzero Fr salt. It recomputes fold(OP,[domain,6,slot,account,spendNonce,tokenIndex,amount,nonce,0,salt])

publishProvenTransition(signals,operations,accountDA,poolDA,proof) has no operator authorization. publishProvenTransitionAndWithdraw adds one opening and atomically accepts the proof and pays. withdrawProven redeems an existing accepted claim. Only msg.sender == account receives funds; spent commitment and used nonce are marked before transfer, atomically with payout/inbox. Claims do not expire and remain valid across later roots/operator rotations. Existing per-token withdrawal pause remains. Kind5/6/7 and redemption do not depend on whitelist/market pause

Successful deposits/payouts append immutable inbox records kind2/7 with monotonic eventId. Publication consumes their exact sequential prefix, so a prover cannot invent/skip a bridge event. ZK deposit requires the owner's whitelist, accepted owner registration, supported token/amount and an unpaused market. REGISTER requires the registering owner's whitelist before owner/slot registry writes, but not an unpaused market. Whitelist belongs to the operation owner, not the proof publisher: an unlisted relayer can still publish a valid authorized transition. An accepted canonical DEPOSIT kind2 is still consumed after revocation, same as SETTLE_WITHDRAWAL kind7, so inbox consumption never depends on current admission. SWAP/ADD_LP retain contract-enforced whitelist/market pause checks. The old signed withdraw, publishBatch, publishSignedBatch and six-argument publishZkTransition revert in the new Vault. Kind8 is prohibited at contract/engine/API boundaries even though historical Circom can express it

## DA and receipts

For each operation publish `{kind,slot,owner,newLeaf,ciphertext[7]}`. Account ciphertext plaintext order: `[ruba,usdt,shares,spendNonce,pendingRuba,pendingUsdt,salt]`. keyCommit=H(KEY,key). stream[j]=fold(STREAM,[key,newLeaf,j]); cipher[j]=plain[j]+stream[j] in Fr. Circuit verifies the key commitment and correct encryption of the updated account. New leaf salt must be freshly randomized for accepted mutations; newLeaf is the PRF nonce. NOP DA records are all zero. Public registry binds owner/slot once; recoveryKeyCommit is bound by the owner-signed REGISTER commitment and proven immutable account leaf, not a separate unbound calldata registry field. Publication cannot register a second slot for the same owner. Runtime slot allocation must fail on collision. Final pool data is encrypted similarly using its private recovery key and poolHash as nonce: `{poolHash,poolCiphertext[6]}`. Its keyCommit is pinned in the domain/genesis. DA digest = fold(DA,[domain,stateVersion,...each(kind,slot,owner,newLeaf,...ciphertext), poolHash,...poolCiphertext]). All actual values are supplied in calldata, not just a hash/CID

Receipt v2 uses field-native fold(RECEIPT,[2,chainId,vault,tradeId,owner,tokenIn,tokenOut, amountIn,amountOut,feeNumerator,feeDenominator,reserveRubaBefore,reserveUsdtBefore, reserveRubaAfter,reserveUsdtAfter,salt]). Four leaves use ordered H(left,right) Merkle parents. Circuit binds each receipt to its actual swap and produces receiptsRoot. Control receiptsRoot=0. Legacy receipt parsing may remain for historical files; v2 cannot reuse Keccak verification

## Manual closure and retained assumptions

The existing signed RubaMarketControl command `{kind:"closeBatch",marketId}` authorizes the server to seal the selected market. It uses the administrator signer, control nonce and deadline. It grants no authority to forge owner signatures or bypass admission. Proof publication itself remains permissionless and is paid by the submitting wallet. A regulator receives selected receipt openings and Merkle paths separately; sealing does not publish those plaintexts

What we assume on purpose: the admin and prover are available and someone is willing to pay gas, there is no close timer, and a sealed tail is not rebuilt automatically if a pause or whitelist revocation makes an operation invalid before publication. Such a transition can still fail and block dependent transitions. Closure is not a server-independent or censorship-resistant exit. Partial packets give a smaller mixing set; even four do not guarantee privacy against metadata/reserve analysis. The current Sepolia contracts stay as they are until we deploy replacements

## Recovery / persistence / tests

Persist economic transition+authorization+private witness atomically with the engine mutation. On restart, recompute/check accepted checkpoint against onchain root and replay pending journal; never turn arbitrary current DB content into a new accepted genesis/root. Owner backup includes recovery key, chain/vault, slot/keyCommit, latest leaf preimage/path/root, accepted stateVersion/block, pending authorizations and owner-held withdrawalClaims[] openings. Save each opening locally BEFORE HTTP/wallet requests; its signature can initially be absent. Validate canonical chain/vault/domain/owner/slot, hash, amount/ranges, nonce equality and salt. Acceptance/spent status comes only from withdrawalClaims/spentWithdrawalCommitments reads, never from uploaded JSON. Verify locally; never auto-resend on import. Published DA permits owner reconstruction of their account and Merkle path without the API. Encrypted operator checkpoint backups may assist full-server restoration; key loss remains a limitation. Account DA reveals aggregate pending balances only: it cannot reconstruct a lost claim nonce/salt. An accepted saved opening can be redeemed directly without Web2; a balance backup alone cannot. Offline proving of new transitions and emergency escape remain deferred in docs/DECISIONS.md

Tests cover real witness and proof generation, JS verification, deployed Solidity verification, forged math/owner/nonce/membership/receipts/inbox/DA rejection, state chain continuity, old setters disabled, user-paid proof-only publication, restart/recovery and perpetual proof-reservation redemption. Test owner/token/amount/nonce/salt tampering, replay, atomic/standalone payout, operator rotation/delay, rejection of non-whitelisted registration/new deposits, accepted registration before deposits, revocation before publication/deposit, unlisted relayer publication, post-revocation credit/LP removal/withdrawal and disabled kind8/legacy paths
